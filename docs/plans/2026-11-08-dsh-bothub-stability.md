# BotHub：多窗口预览与持续运行验收

本轮承接桌面显示器需求，并补原计划 P4 的部分多窗口稳定性证据。

## 设计

- 同一浏览器存储分区、同一 `api/bot` 路径、同一 Bot 的被动 PNG 采集，使用 Web Locks 排队。
- 正常采集持有锁至少一秒，或直至截图完成；画面立即交给当前窗口，冷却期不延迟展示。不同 Bot 不互相阻塞。取消会立即结束冷却，因此窗口切换期间可出现短于一秒的间隔。
- 排队和在途截图复用现有取消/超时信号。页面隐藏、关闭、切换和卸载时取消；冷却等待可被立即中断。不会把图片、登录状态、控制票据写入锁、广播或持久化存储。
- 多个窗口分享采集时隙，各自仍通过已认证的预览通道读取。窗口越多，每个窗口的刷新越慢；现有五秒过期规则继续生效。
- 未提供 Web Locks 或存储策略禁用它时，退回已有单窗口限制。不同浏览器、不同 profile/存储分区以及原生 DS Bot 面板不参与协调；本轮不是服务端全局限流。
- 不新增宿主接口，不启动或接管桌面，不改变 idle 时间。真实容器及视频流另行验收。

## 验收计划

1. 单元测试：同 Bot 互斥和一秒间隔、不同 Bot 独立、排队/采集中/冷却中取消、拒绝后无重复调用、缺少能力的降级、长时间循环清理。
2. 实际浏览器与 Computer service + 测试 provider：至少三个窗口同时预览同一 Bot，记录服务端采集时间/峰值并发/每窗口新帧；关闭、隐藏、重载后检查锁与资源释放。
3. 隔离真实 DSH + mock 团队：多个 BotHub 页面持续运行，切换 2D/3D、开关预览、离线/恢复、刷新；检查连通性、错误、请求和卸载。此项不证明真实模型或真实桌面容器性能。
4. 两插件单元测试、生成检查和 lint；本轮不改 host，不重复宣称此前 51/52 smoke 已全绿。

当前 Docker daemon 不可连接，不能将测试 PNG 的结果记录为真实容器验收。

## 验收中发现的连接占用问题与设计补充

隔离真实宿主中，三个页面同时开启原生 DSH 连接和 BotHub SSE 后，
`computer-state` 请求在 3008ms 超时；关闭一个页面后同一请求 29ms 返回
`bot/computer-off`。桌面本来未配置，窗口却显示「桌面暂不可用」。
证据为 `.playwright-mcp/bothub-stability/connection-diagnosis.json`。
这是请求连接被常驻流占用的复现，不是桌面 provider 故障。

为同一浏览器存储分区和同一监控路径保留 **一个 BotHub SSE**：

- 用独立 Web Lock 非阻塞抢占；其他页面立即走已有的认证快照轮询，
  无需等待失败重试，不显示连接中断，也不把其他窗口的数据当作当前窗口数据。
- 轮询页面沿用每 2.5 秒更新、每 12 次轮询重新尝试实时流的策略；
  实时页面隐藏、关闭、重载或断线时释放锁，其他页面可接替。
- 缺少锁支持/存储策略拒绝时使用轮询；这是兼容性降级，不自行新增持久化选主协议。
- 流读取取消时立即释放占用，即使底层 transport 没有响应取消也禁止它发布迟到帧。
- 画面截图锁与监控流锁分别管理，避免互相占用。此变更不修改 DSH、
  不跨页面广播监控数据、不新增服务端权限入口。
- 轮询提示统一为「正在定期检查更新」，适用于网络降级和多窗口共享连接。

验证边界：此方案限制 BotHub 自己的常驻流，不能控制其他插件、原生 DSH 或
其他浏览器/profile 的连接；不声称任意数量窗口都不会耗尽浏览器连接。

## 后续视频流接入条件

仓库已有 DS Bot 原生 `openViewer` 通道，但当前打开/关闭会更新 `touched`，
且 `reapIdle` 会跳过仍有 viewer 的桌面。直接套用到后台工位会改变自动休眠，
因此本轮继续使用被动 PNG，不通过提高截图频率冒充视频流。

下一批需要先在 DS Bot 插件中定义显式的被动视频能力：不能携带控制票据、
不能刷新 idle、不能阻止回收；停止/重绑定必须关闭被动流。之后才能为放大
窗口接入只读流并保留 PNG 降级，同时验收真实容器、连接配额、断线/隐藏和
多窗口。工位小屏继续使用受限截图，不默认给每个工位开启完整视频通道。
